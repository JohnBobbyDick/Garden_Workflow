# Обращение к LLM: прокси, ротация ключей, ретраи

Документ описывает, как бэкенд ходит в модель (Google Gemini или Ollama), как выбираются ключи и прокси,
как определяется протокол прокси и как устроены повторные попытки.

Основной код:

| Файл | Что делает |
|---|---|
| `backend/ai/llm_client.py` | `generate()` — единая точка входа; цикл попыток, HTTP-запрос к Gemini/Ollama, маскировка секретов |
| `backend/ai/gemini_pool.py` | Разбор `GEMINI_*` из окружения: списки ключей, прокси, моделей, число попыток |
| `backend/ai/proxy_scheme.py` | Автоопределение протокола прокси (`auto://`) и кэш удачного протокола |
| `backend/ai/ai_analyzer.py` | Фичи (объяснение дефекта, фикс ошибки, советы, ревью) поверх `generate()`; «ремонтные» раунды и статический фолбэк |
| `backend/api/ai.py` | HTTP-эндпоинты `/api/ai/*` |
| `backend/check_llm.py` | Диагностика: по одному запросу через каждый прокси/протокол и напрямую |
| `backend/config.py` | Читает `backend/.env` (реальные переменные окружения имеют приоритет) |

---

## 1. Общая схема запроса

```
UI (axios) ──► /api/ai/<feature> ──► ai_analyzer.<feature>()
                                         │
                                         ├─ собирает промпт из prompts/<lang>/<name>.txt
                                         ▼
                              llm_client.generate(prompt, validate=…)
                                         │
                     ┌───────────────────┴───────────────────┐
              provider=ollama                         provider=gemini
           одна попытка, без прокси          цикл из N попыток (раздел 4):
                                             ключ × прокси × протокол × модель
                                                         │
                                                         ▼
                              POST {GEMINI_BASE_URL}/models/{model}:generateContent
                                   заголовок x-goog-api-key, через выбранный прокси
```

`generate()` возвращает текст ответа или бросает `LLMUnavailable`. Любая фича ловит это исключение и
отдаёт пользователю статический совет из базы паттернов (`static_tips`) с полем `note`, где написана причина
(авто-ревью в этом случае просто молчит).

## 2. Настройка (`backend/.env`)

Шаблон — `backend/.env.example`. Списки разделяются запятой, `;` или пробелом; дубликаты и пустые элементы
отбрасываются; значения с `#` нужно брать в кавычки.

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `LLM_ENABLED` | `false` | Без `true` LLM считается выключенным, `generate()` сразу бросает `LLMUnavailable` |
| `LLM_PROVIDER` | `gemini` | `gemini` или `ollama` |
| `GEMINI_API_KEY` | — | Список ключей. Для Gemini без ключей LLM считается ненастроенным |
| `GEMINI_KEYS_COUNT` | все | Использовать только первые N ключей списка |
| `GEMINI_MODEL` | `gemini-2.5-flash` | Модель первой попытки |
| `GEMINI_FALLBACK_MODELS` | `gemini-2.5-flash,gemini-2.5-flash-lite` | Модели следующих попыток (дубликат основной выкидывается) |
| `GEMINI_MAX_RETRIES` | авто | Число попыток; авто-формула — в разделе 4 |
| `GEMINI_PROXIES` | — | Список прокси; пусто = прямое соединение |
| `GEMINI_PROXY_SCHEME` | `auto` | Протокол для записей без схемы: `auto` / `http` / `https` / `socks5` / `socks5h` |
| `GEMINI_PROXY_PORT` | — | Порт для записей вида `ip:login:password` |
| `GEMINI_BASE_URL` | `https://generativelanguage.googleapis.com/v1beta` | Базовый URL API (можно подменить, например, на свой релей) |
| `OLLAMA_URL` / `OLLAMA_MODEL` | `http://localhost:11434` / `codellama:7b` | Локальная модель |

Состояние можно посмотреть через `GET /api/ai/status` (включено ли, провайдер, основная модель).

## 3. Прокси

### 3.1. Формат записей (`gemini_pool.parse_proxy`)

| Запись | Результат |
|---|---|
| `host:port:login:password` | `<scheme>://login:password@host:port` |
| `host:login:password` | то же, порт берётся из `GEMINI_PROXY_PORT` (если пусто — без порта) |
| `socks5://user:pass@host:1080` (любой полный URL) | используется как есть, схема фиксирована |
| что-то другое | запись молча отбрасывается |

- Пароль может содержать `:` — всё после третьего двоеточия считается паролем.
- Логин и пароль percent-кодируются (`quote(..., safe='')`), поэтому спецсимволы в них безопасны.
- `<scheme>` — значение `GEMINI_PROXY_SCHEME`; при `auto` запись хранится как `auto://…` и протокол
  определяется перед каждым запросом.

Для SOCKS используется `httpx` + `socksio` (есть в `requirements.txt`).

### 3.2. Автоопределение протокола (`proxy_scheme.resolve`)

Для записи `auto://login:pass@host:port` перед попыткой вызывается `resolve(url, tried)`, где `tried` —
протоколы, уже опробованные для этого прокси **в текущем вызове `generate()`**:

1. **Кэш.** Если для `host:port` есть запомненный протокол моложе 10 минут (`CACHE_TTL = 600`) и он ещё не
   пробовался в этом вызове — берётся он, без сетевых проверок.
2. **Сниффинг порта** (`sniff`, таймаут 3 с на соединение и на чтение, **логин/пароль не отправляются**):
   - шлётся SOCKS5-приветствие `05 01 00` («без аутентификации»); если первый байт ответа `0x05` → `socks5`;
     если ответ начинается с `HTTP/` → `http`;
   - иначе шлётся `CONNECT generativelanguage.googleapis.com:443 HTTP/1.1`; ответ `HTTP/…` → `http`;
   - порт молчит или отвечает чем-то другим → «не определено».
   Определённый протокол берётся, если он ещё не пробовался.
3. **Перебор.** Иначе берётся первый неопробованный из `http` → `socks5` → `https`.
4. Если пробовали всё — `tried` очищается и цикл начинается заново (с определённого протокола или `http`).

После попытки:
- успех (HTTP 200 с непустым текстом) → `remember()`: протокол кладётся в кэш на 10 минут;
- провал → `forget()`: запись удаляется из кэша, следующая попытка снова сниффит/перебирает.

Кэш живёт в памяти процесса (общий для всех запросов, сбрасывается при рестарте).
Прокси с явной схемой (`http://…`, `socks5://…` или фиксированный `GEMINI_PROXY_SCHEME`) не сниффятся и не кэшируются.

### 3.3. Выбор прокси на попытку

`_select_unused(proxies, used_proxies)`: случайный прокси из ещё не использованных в этом вызове; когда
использованы все — случайный из всего списка (с предупреждением в логе). Без `GEMINI_PROXIES` запрос идёт напрямую.

## 4. Ретраи (`llm_client.generate`)

### 4.1. Число попыток

Если `GEMINI_MAX_RETRIES` задан и > 0 — используется он. Иначе:

```
candidates = Σ по прокси: 2, если запись auto://, иначе 1
retries    = min(max(кол-во ключей, candidates, 3), 6)
```

То есть по умолчанию от 3 до 6 попыток — столько, чтобы по возможности попробовать каждый ключ и каждую
пару «прокси × протокол». (Комментарий в `.env.example` про «max 5» устарел — в коде потолок 6.)

### 4.2. Что меняется от попытки к попытке

| Параметр | Правило |
|---|---|
| Модель | `models[min(attempt, len(models)-1)]`: 1-я попытка — `GEMINI_MODEL`, дальше — фолбэки по порядку, последняя модель повторяется до конца. По умолчанию: `flash` → `flash-lite` → `flash-lite` … |
| Ключ | Случайный из неиспользованных в этом вызове; когда кончились — случайный из всех |
| Прокси | Случайный из неиспользованных; когда кончились — случайный из всех |
| Протокол прокси | См. 3.2 (для одного и того же прокси протоколы в рамках вызова не повторяются, пока не исчерпаны) |
| Пауза перед попыткой | Линейно растёт: 2 с, 4 с, 6 с, 8 с, 10 с (`FIRST_SLEEP = 2`, `SLEEP_STEP = 2`). Перед первой попыткой и после последней паузы нет |

Состояние «использованных» ключей/прокси/протоколов локально для одного вызова `generate()`; между
вызовами переносится только кэш протоколов из 3.2.

### 4.3. Что считается неудачной попыткой

Любое из перечисленного превращается во внутреннее `_AttemptFailed` и ведёт к следующей попытке:

- HTTP-статус ≠ 200 (в т.ч. 429, 403 «User location is not supported», 5xx) — сообщение берётся из
  `error.message` ответа API, обрезается до 200 символов;
- пустой текст в `candidates[0].content.parts`;
- битый/неожиданный JSON ответа (`KeyError`, `IndexError`, `ValueError`, `TypeError`);
- сетевые ошибки `httpx` (отказ соединения, ошибка прокси, TLS и т.п.);
- таймауты (см. 4.4);
- ответ не прошёл `validate(text)` — каждая фича передаёт свою проверку (например, в JSON должно быть поле
  `explanation` / `suggestion` / `advice`, а для ревью — список `suggestions`).

Ретраи не различают типы ошибок: даже 400 (кривой запрос) будет повторён на другом ключе/прокси/модели.

Когда попытки кончились — `LLMUnavailable("Все N попытки исчерпаны. Последняя ошибка: …")`
(при `retries == 1` — просто текст ошибки).

### 4.4. Таймауты одной попытки

- `timeout` по умолчанию 30 с (общий таймаут httpx на чтение/запись);
- `connect` — `min(timeout, 10 с)`: мёртвый прокси отваливается быстро, а не через 30 с;
- жёсткий дедлайн `asyncio.wait_for(..., timeout + 5)` — на случай, когда несовпадение протокола
  (SOCKS ↔ HTTP) подвешивает рукопожатие ниже таймеров httpx;
- плюс до ~12 с на сниффинг `auto://`-прокси (две пробы по 3 с на соединение + 3 с на чтение).

Оценка худшего случая для Gemini при 6 попытках: 6 × ~35 с + паузы 30 с ≈ 4 минуты (+ сниффинг).
Фронтенд ждёт меньше: обычные AI-запросы — 90 с (`frontend/src/hooks/useApi.ts`), авто-ревью — 120 с
(`useAutoReview.ts`), так что UI может сдаться раньше, чем бэкенд исчерпает попытки.

### 4.5. Ollama

Одна попытка, без прокси, ключей и пауз: `POST {OLLAMA_URL}/api/generate` (`stream: false`, при JSON-режиме
`format: "json"`). Любая ошибка или непрошедший `validate` → сразу `LLMUnavailable`.

## 5. Тело запроса к Gemini

```json
POST /models/{model}:generateContent
x-goog-api-key: <ключ>

{
  "contents": [{"parts": [{"text": "<промпт>"}]}],
  "generationConfig": {"temperature": 0.2, "responseMimeType": "application/json"}
}
```

`responseMimeType` ставится, когда `as_json=True` (так вызывают все фичи). Ответ — конкатенация `text` всех
`parts` первого кандидата. Затем `parse_json()` терпимо извлекает объект: срезает ```` ``` ````-ограждения
и прозу вокруг, берёт текст от первой `{` до последней `}`; при неудаче возвращает `{}`.

Ключ передаётся только заголовком, не в URL — поэтому не попадает в тексты исключений httpx и логи.

## 6. Уровень выше: «ремонтные» раунды (`ai_analyzer._generate_patches`)

Это отдельный цикл **поверх** ретраев `generate()` — для фич, которые предлагают правку кода
(объяснение дефекта, фикс синтаксической ошибки, авто-ревью):

1. Запрос к модели (внутри — до N сетевых попыток из раздела 4).
2. Из ответа строятся патчи (`patcher.build_patch`) и проверяются: применяются ли, компилируется ли результат,
   не появилось ли новых ошибок.
3. Если модель вернула правки, но **ни одна** не валидна — к исходному промпту дописывается
   `prompts/<lang>/repair.txt` со списком проблем (до 1500 символов) и запрос повторяется.
4. Максимум `REPAIR_ROUNDS = 2` дополнительных раунда (всего до 3 запросов к модели).
5. `LLMUnavailable` пробрасывается наружу, только если упал самый первый запрос; на ремонтном раунде —
   просто возвращается последний полученный результат.

Итого в худшем случае одна кнопка может породить 3 × N HTTP-запросов к Gemini.

## 7. Защита ключей и нагрузки

- **Маскировка секретов** (`_scrub`): из любого текста ошибки, идущего в лог или в `note` для UI, вырезаются
  ключи и логин/пароль прокси (во всех вариантах схемы). В логах — только `scheme://host:port` прокси
  (`mask_proxy`) и последние 4 символа ключа.
- **Авто-ревью**: не больше 2 одновременных ревью на процесс (`asyncio.Semaphore(2)` в `api/ai.py`).
  Если пользователь снова начал печатать и UI оборвал запрос (`AbortController`), бэкенд раз в 0,5 с проверяет
  `request.is_disconnected()` и отменяет задачу — оставшиеся ретраи не тратят ключи.
- **Песочница**: дочерние процессы, исполняющие пользовательский код, получают минимальное окружение —
  `GEMINI_*` и прокси им не видны.

## 8. Логи и диагностика

В логгере `ai`:

```
Gemini attempt 1/4: model=gemini-2.5-flash key=...a1b2 proxy=socks5://1.2.3.4:1080
Gemini attempt 1/4 failed: таймаут 30 с: прокси/сеть не отвечает
All proxys were used, resetting and selecting a random one
```

Проверка конфигурации на целевой машине:

```bash
cd backend && python check_llm.py
```

Скрипт печатает настройки (кол-во ключей, прокси, модели, retries), затем шлёт по одному маленькому
запросу первым ключом через каждый прокси — для `auto://` по каждому протоколу `http`, `socks5`, `https`,
`socks5h` — и напрямую, с `OK`/`FAIL`, временем и причиной. Нужен хотя бы один `OK`.

Типичные ошибки:

| Сообщение | Причина |
|---|---|
| `LLM вернул ошибку 400: User location is not supported…` | Регион выхода прокси/сервера не поддерживается Gemini |
| `LLM вернул ошибку 429…` | Исчерпана квота ключа — помогает больше ключей |
| `не удалось подключиться (за 30 с)` / `нет ответа` | Прокси недоступен или не тот протокол — проверьте `GEMINI_PROXY_SCHEME` |
| `таймаут 30 с: прокси/сеть не отвечает` | Сработал жёсткий дедлайн — чаще всего несовпадение протокола |
| `LLM отключён или не настроен` | `LLM_ENABLED≠true` или пустой `GEMINI_API_KEY` |

На локальной машине с VPN в режиме TUN проверка прокси бессмысленна — VPN перехватывает соединения.

Тесты логики ретраев: `backend/tests/test_llm_retries.py`.
