### Фаза 1 — анализаторы

- **SECRET** — 5 слоёв: сигнатуры, имена и стоки, константный резолвер Kotlin AST, fallback, энтропия. Плюс YAML/properties/JSON/XML. Маскируются значение, каждый литерал-фрагмент и тело PEM.
- **SCA** — разбор Gradle Kotlin DSL по AST: `val`, `extra`, `by project`, `gradleProperty`, version catalog, `platform`. Также Groovy, `include` из settings, приоритет lockfile, справочник с валидацией по схеме, собственные сравнение версий и калькулятор CVSS v3. Чтение файлов только через `safe_file` (без symlink и `..`).
- **SAST** — модель Spring: маршруты и правила `SecurityFilterChain` (первое совпадение). Граф вызовов через DI-поля, межпроцедурный taint. 12 правил: 5 обязательных и 7 дополнительных, включая `csrf-disabled`.
- **Экспорт**: `submission.json` строго по формату организаторов (фильтр confidence, без транзитивных), собственный валидатор с CLI, Markdown и HTML.
- **Eval** (`make test-eval`):
  - учебный набор — **15/15**, 0 сработавших контролей, 0 лишних находок;
  - 3 мутанта (`library-loans`, `clinic-appointments`, `parcel-lockers`) — 46/46, 0 контролей, 0 лишних.
  - Мутанты выявили три пробела обобщения, все исправлены общими правилами с регрессионными тестами:
    - Principal, который только пишется в лог, принимался за проверку владельца;
    - id терялся при передаче через `MapSqlParameterSource`;
    - координаты Maven считались строками, похожими на секрет.
- **Распараллеливание**: экспорт и генерация мутантов выполнялись фоновыми агентами параллельно с SAST.
- **Гейт**:
  - `pytest tests/unit` — 254 passed; `pytest -m eval` — 4 passed;
  - grep по запрещённым именам в `backend/app` пуст;
  - валидатор принимает `submission.json` учебного набора;
  - `ruff` чист.
- **Решения фазы**:
  - Отдельный regex-режим разбора Kotlin не делался: tree-sitter устойчив к синтаксическим ошибкам и строит частичное дерево; Groovy DSL разбирается регулярными выражениями.

  - В мутант `clinic-appointments` добавлена ожидаемая находка `csrf-disabled`: это реальная проблема (CSRF отключён при httpBasic), которую нашёл анализатор.
  - AI-раздел отчётов подключается в фазе LLM.
- **Фоновые ревью безопасности** нашли 7 проблем, все исправлены с тестами:
  - symlink и `..` в читателях SCA;

### Фаза 3 — безопасность платформы и многопользовательность

- **Аутентификация**:
  - регистрация и вход, пароли argon2 с проверкой постоянного времени для несуществующих e-mail;
  - JWT access на 15 минут; refresh с ротацией и обнаружением повторного использования — отзывается всё семейство;
  - `logout`, `GET/PATCH /auth/me`;
  - rate limit на вход по паре (IP, e-mail); CORS строго по `APP_CORS_ORIGINS`.
- **Workspaces**:
  - роли `admin`/`developer`/`viewer`;
  - приглашения: одноразовый токен, хранится хэш;
  - смена роли и удаление участника с защитой последнего администратора.
- **Изоляция**: каждый объект проверяется на принадлежность к workspace; чужие объекты отдают 404, недостаточная роль — 403. IDOR-матрица на 16 эндпоинтах; чужой проект и чужие credentials нельзя привязать к своему сценарию.
- **Credentials**:
  - AES-256-GCM с версиями ключа; dev-ключ генерируется с предупреждением, вне dev ключ обязателен;
  - значения только на запись, ответ API — `••••` + последние символы.
- **Masker**:
  - покрывает логи (фильтр на root/uvicorn), `run_events`, ошибки API, сохранённые находки, отчёты и уведомления;
  - после рестарта значения из хранилища заново регистрируются в маскере (`preload_credentials` в API и воркере).
- **SSRF и repo-guard** — см. фазу 2. Флаг `allow_write` выставляет только admin, факт пишется в аудит. Для репозитория организаторов запрет зашит в коде (`is_readonly_repo`) и возвращает 403 `readonly_repository`.
- **Аудит**: вход (успешный и неудачный), регистрация, credentials, allowlist (add/remove/write_flag), загрузки, участники; `GET /workspaces/{id}/audit`.
- **Прочее**: безопасные заголовки (CSP, X-Frame-Options, nosniff…), лимит тела запроса (413). Анализаторы не исполняют код проекта — это проверяет тест на отсутствие `subprocess`/`eval`/`exec` в `app/analyzers`.
- **Гейт**:
  - `tests/security` — 11 passed; среди них тест-канарейка: токен бота, который mock-сервер Telegram возвращает в тексте ошибки, не находится ни в одной таблице БД, ответе API, SSE и логах;
  - полный прогон — 443 passed, 3 skipped; `ruff` чист.
- **Ручная проверка на стеке**:
  - `https://github.com/torvalds/linux` → 422 `source_not_allowed`;
  - `file:///etc/passwd` → 422; репозиторий организаторов принят;
  - значение токена Telegram не найдено ни в ответах API, ни в `api.log`, ни в таблицах SQLite, ни в журнале mock-сервера.

### Фаза 4 — интеграция LLM

- **Провайдеры** (`app/ai/providers/`, новый провайдер — новый класс с `@register_provider`):
  - `openai_compat`: `response_format` с JSON-схемой → `json_object` → инструкция с разбором. Если сервер отвергает `response_format`, сразу переходим к инструкции;
  - `ollama`: `/api/chat`, `format` — схема;
  - ретраи с backoff на 429/5xx/таймауты (с учётом `Retry-After`), явные `LLMError`/`LLMTimeout`;
  - все запросы идут через SSRF-guard. Локальный адрес провайдера разрешает только admin флагом «разрешить локальный адрес»; для `ollama` по умолчанию разрешён `localhost:11434`.
- **Настройки**:
  - `GET/PUT /settings/ai` (по умолчанию выключено, подсказки о бесплатных вариантах);
  - `POST /settings/ai/test` (список моделей + пробный JSON-запрос), `GET /settings/ai/models`;
  - ключ хранится только ссылкой на зашифрованный credential; переопределить провайдера можно в ноде `ai.report`.
- **Схема и промпты**: `ai/schemas.py`, `ai/prompts.py` (RU/EN). Запрещено выдумывать id, файлы, строки, CVE/GHSA; `fix.before` должен быть дословной копией строк из поля `code`. В LLM уходят только маскированные данные: маскированное представление файла плюс маскер запуска.
- **Валидатор** (`ai/validator.py`):
  1. схема плюс одна попытка авто-исправления с текстом ошибки;
  2. id находок существуют, без дублей; неизвестные отбрасываются, в том числе в `priority_order`;
  3. `fix`: файл находки или её `alternate_locations`, строки в пределах файла, `before` совпадает с маскированным текстом, в `after` нет масок;
  4. CVE/GHSA — только из (справочник ∩ находки запуска), остальные вырезаются, ставится флаг `hallucinated_ids`;
  5. `safe_version` берётся только из `fixedVersions`, иначе исправляется;
  6. ссылки `файл:строка` в тексте проверяются.
  Шаги и метрики (`valid_items/total_items`, `dropped`, `fixes_kept/dropped`, `hallucinated_ids`, `repair_attempts`, `filled_deterministic`) сохраняются вместе с отчётом.
- **Сервис и нода `ai.report`**:
  - находки разбиваются на пачки по размеру;
  - находки, которые LLM не объяснила, дополняются детерминированно с пометкой `source: deterministic`;
  - `fallback_to_deterministic` включён по умолчанию: отчёт помечается `ai_generated: false` и хранит причину. Если fallback выключен, нода падает с явной ошибкой;
  - отчёт хранится в `ai_reports` (провайдер, модель, токены, валидация); `GET /runs/{id}/ai-report`.
- **Отчёты**: в `report.md` и `report.html` появился раздел «AI-объяснение и рекомендации» («…(без AI)» для fallback): индикатор доверия, порядок исправления, объяснения, diff-фиксы, общие рекомендации. Уведомления содержат вывод AI.
- **Гейт**:
  - `tests/ai` — 31 passed. Это контрактные тесты на настоящих локальных HTTP-серверах (OpenAI-compatible и Ollama API): формат запроса, заголовки, JSON-режимы, деградация режима, 429/5xx, таймаут, отказ без ретраев на 401, SSRF. Плюс валидатор (подсаженные выдуманные CVE/GHSA, неизвестные id, неверный путь/строки/`before`, маска в `after`, неверная `safe_version`, несуществующая ссылка) и fallback;
  - `tests/api/test_ai_api.py` — 7 passed (настройки, тест соединения, E2E с AI-разделом в отчёте, fallback при отказе провайдера, переопределение провайдера в ноде, 404/IDOR);
  - полный прогон — 481 passed, 3 skipped.
- **Живой прогон на реальной LLM не выполнен.** В окружении нет установленной LLM: Ollama и LM Studio есть только в PATH, бинарников нет, локальных моделей нет. Ключа внешнего API тоже нет. Устанавливать ПО и скачивать модели без согласия пользователя не стали. Качество ответов реальной модели не измерено. Переключиться на реальную модель можно только настройками, без правки кода — это проверено тестом смены провайдера. *(Позже выполнено на облачной модели NVIDIA Nemotron — см. раздел 4 «Проверка облачного API NVIDIA» и раздел 8.)*

  ловили. Новые тесты `test_gzip_response_is_decoded_once_{direct,via_proxy}` были красными, после правки — зелёные.

## 4. Ограничения и непроверенное

- **Локальная LLM не запускалась.** В окружении разработки не было Ollama и LM Studio. Загрузку Ollama в Compose
  пользователь отложил: модель будет на другом компьютере. AI-слой (отчёт, валидатор, генерация сценариев, AI-план,
  AutoFix) проверен контрактными тестами на локальных HTTP-серверах в форматах OpenAI и Ollama, в демо без модели
  работает детерминированный fallback. Живой прогон облачной модели на одной находке описан в разделе 8.
- **Реальные Telegram, SMTP, GitHub и GitLab не проверялись.** Интеграции проверены на mock-серверах, повторяющих их
  HTTP-API (`scripts/mock_services.py`, `scripts/mock_scm.py`). Клонирование публичного репозитория организаторов
  с GitHub проверено вживую.
- **Восстановление `git_url` для PR AutoFix** на точном коммите реализовано, но автотестом не покрыто.
- **Rate limit входа** хранится в памяти процесса. За nginx фактически действует на e-mail (см. `docs/SECURITY.md`).
- **SAST — только Kotlin/Spring**, SCA — Gradle (Kotlin DSL, Groovy DSL, version catalog, lockfile) по локальному
  справочнику.
- **Скрытая вариация** организаторов недоступна. Устойчивость оценена на трёх собственных мутантах с теми же классами
  проблем (раздел 2).
- **Противоречия источников.** `prompt.md` требует все три канала уведомлений, AutoFix, score и diff-aware, а PDF —
  один канал и три звёздочки. Реализовано по более строгому `prompt.md`. PDF разрешает готовые workflow-движки
  (Temporal, Flowable). Команда сознательно написала собственный движок на asyncio с очередью в PostgreSQL: меньше
  инфраструктуры, полный контроль над событиями для живой визуализации, IF/ELSE-пропусками и маскированием данных
  между нодами.
- **Демо-скрипты diff-aware и AutoFix** работают на dev-стеке: они поднимают собственный mock GitHub и временные
  git-репозитории.

## 6. Пользовательские ноды и обработка находок

В палитре «Ноды» разработчик или администратор пространства может сохранить именованное преобразование JSON.

после группировки находок поле `review` с правилом `=counts.HIGH > 0` можно использовать в следующей
ноде IF/ELSE как `data.review`. Определения сохраняются в таблице `custom_nodes`. Экземпляр в графе содержит
копию правил, поэтому экспорт и повторный запуск сохраняют его поведение.

## 10. Сверка с требованиями организаторов (репозиторий `TBagirov/training` и PDF)
