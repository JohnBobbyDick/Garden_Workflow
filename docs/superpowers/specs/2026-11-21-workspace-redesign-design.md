# Рабочее пространство «конструктор в центре» — дизайн

Дата: 2026-11-21. Статус: на согласовании.

## 1. Зачем

Команда посмотрела на интерфейс после переноса макета Figma и решила: он перегружен и неудобен. Главное в продукте —
конструктор графов. Он должен быть самым красивым и удобным местом сервиса. Сейчас до него долгий путь: проект →
шаблоны → шаблон → вписать путь на сервере → «Использовать». Результаты разбросаны по четырём страницам.

Кто пользуется: **жюри хакатона**. Они сами откроют сервис и проверят его на **собственном новом репозитории**
(скрытая вариация учебного проекта). Терминов платформы они не знают, инструкции читать не будут. За пару минут
они должны пройти от «вот мой код» до графа с живым выполнением и понятными результатами. Макет Figma больше не
обязателен.

## 2. Цели, не-цели, анти-цели

**Цели**
- Один экран-рабочее пространство: холст в центре, всё остальное вокруг него (как в n8n — ТЗ прямо на него ссылается).
- Путь до первого запуска на своём репозитории — **не больше 3 действий** после входа: вставить ссылку (или zip) →
  выбрать «готовый сценарий» → «Запустить».
- Красивое, плавное выполнение. Неоновая переливающаяся обводка работающей ноды, ход данных по рёбрам, понятный
  финал — от первой ноды до последней.
- Сохранить **всё**, чего требует ТЗ (раздел 4), и все наши функции. Меняется место и вес функций в интерфейсе,
  а не их наличие.

**Не-цели**
- Новые анализаторы, ноды, изменения движка исполнения.
- Мобильная версия (адаптивность до ≥1280 px; на меньших экранах сервис должен оставаться рабочим, но не идеальным).
- Сохранение вёрстки Figma-макета.

**Анти-цели (провал, даже если «работает»)**
- Жюри вставило ссылку на свой репозиторий и получило ошибку allowlist.
- Функция ТЗ пропала из интерфейса или спрятана так, что её не найти за 10 секунд (шаблоны, CI/CD, история,
  AI-генерация, живые данные между нодами).
- Анимации тормозят холст или мешают читать граф; анимации без `prefers-reduced-motion`.
- Перестали работать ссылки из уведомлений и CI (`/runs/{id}`) или e2e-сценарий из презентации.

## 3. Ограничения

- Правила проекта (`CLAUDE.md`) действуют: никаких заглушек и имитаций; LLM только объясняет; секреты маскируются
  везде; не коммитим; фикстуры организаторов только на чтение; `@xyflow/react` v13 (`changes.applyTo`, нет
  `colorMode`).
- ТЗ: «сканирование допускается только на репозиториях организаторов и собственных учебных проектах». Решение
  пользователя — **вариант А** (раздел 6.1): ссылка на любой публичный репозиторий + обязательное подтверждение,
  с записью в аудит.
- Реальной LLM в окружении нет: AI-генерация показывается, но при отсутствии провайдера объясняет, как его
  подключить; детерминированный отчёт работает.
- Backend-API в основном уже есть. Новое на backend — только раздел 6.

| ⭐ CI/CD | Выдвижная панель «CI/CD» у проверки (YAML, токен, журнал вебхуков) |

| Наши фичи: Diff-aware, Security Score, AI AutoFix, сравнение | Внутри «Итогов» запуска (раздел 5.4) |

## 5. Интерфейс

### 5.1. Каркас

```
┌──────────────┬────────────────────────────────────────────────┬─────────────────┐
│ ✳ Garden     │ payments-api ▾  · Источник: github.com/…  [▶ Запустить] │ ИНСПЕКТОР       │
│              │ [⟲][⟳] [Раскладка] [AI] [⋯ ещё]                       │ (нода / итоги)  │
│ ПРОВЕРКИ     ├────────────────────────────────────────────────┤                 │
│ ● payments   │                                                │                 │
│ ○ demo       │                ХОЛСТ                           │                 │
│ + Новая      │       (палитра: «+» на холсте, клавиша Tab,     │                 │
│──────────────│        или левая кнопка «Ноды»)                │                 │
│ ◷ История    │                                                │                 │
│ ▦ Шаблоны    │                                                │                 │
│ ⇄ CI/CD      │                                                │                 │
│ ▤ Обзор      │                                                │                 │
│ ⚙ Настройки  │                                     [−][+][⤢]  │                 │
└──────────────┴────────────────────────────────────────────────┴─────────────────┘
```

- **Левая колонка** (~240 px, сворачивается до иконок): список проверок (= сценарии), «+ Новая проверка», ниже —
  второстепенные разделы. Они открываются **выдвижными панелями** поверх холста: История, Шаблоны, CI/CD, Обзор
  (бывший дашборд), Настройки. Холст и выбранная проверка при этом не теряются.
- **Шапка холста**: название проверки (переименование по клику), источник кода одной строкой (клик — сменить),
  «Запустить» — главная кнопка. Отмена и повтор, авто-раскладка, AI-ассистент, «⋯» (импорт/экспорт JSON,
  опубликовать как шаблон, удалить, проверить граф). Статус сохранения: автосохранение на сервер, без кнопки
  «Сохранить»; `Ctrl+S` оставляем.
- **Холст** занимает всё оставшееся место. Палитра — **плавающая панель поиска нод**: открывается кнопкой «+»
  (на холсте и на свободном выходе ноды), клавишей `Tab` или кнопкой «Ноды». Перетаскивание из неё на холст
  сохраняется — это требование ТЗ. Добавление по клику на выход ноды сразу ставит новую ноду справа и соединяет
  совместимые порты.
- **Правый инспектор** (~380 px, сворачивается). Режимы:
  - нода выбрана, запуска нет → настройки ноды (форма из JSON Schema, как сейчас);
  - нода выбрана во время или после запуска → её «Данные» (вход/выход) и «Логи»;
  - ничего не выбрано и есть запуск → **«Итоги»** запуска (раздел 5.4);
  - ничего не выбрано и запусков нет → короткая подсказка «что дальше».

### 5.2. Новая проверка (вместо проектов и параметров шаблона)

Одно окно, два шага, всё на одном экране:

```
┌ Новая проверка ─────────────────────────────────────────────┐
│ 1. Что проверяем?                                           │
│   [ https://github.com/team/repo            ] ветка [main]  │
│   ☐ Это учебный или собственный проект — проверка разрешена │
│   ───── или ─────                                           │
│   [ ⇪ Перетащите архив проекта (.zip, .tar.gz) ]                │
│   [ Учебный проект организаторов ]                          │
│                                                             │
│ 2. С чего начать?                                           │
│   ▣ Полная проверка (рекомендуем)   ▢ Только секреты        │
│   ▢ Проверка PR (diff)  ▢ Пустой граф  ▢ Описать словами AI │
│                                                             │
│                       [ Создать и открыть ]  [ Создать и запустить ] │
└─────────────────────────────────────────────────────────────┘
```

- Источник сразу пишется в ноду `source.repo` создаваемого графа (режим `git_url` / `upload` / `path`). Понятие
  «Проект» из основного пути убирается. Существующие проекты продолжают работать (режим источника «проект
  пространства» доступен в инспекторе ноды), но отдельной страницы в главной навигации нет; управление ими
  остаётся в «Настройки → Проекты».
- Карточки «С чего начать?» — это системные шаблоны библиотеки. Параметр источника шаблона заполняется
  **автоматически** из шага 1. Прочие параметры (токен Telegram, адрес почты) **не блокируют** создание: нода
  появляется на холсте с отметкой «нужно заполнить», а запуск объясняет, что именно не заполнено.
- «Создать и запустить» — главный путь для жюри: одно нажатие после ссылки.
- Если проверок ещё нет, это окно показывается сразу после входа на фоне пустого холста.

### 5.3. Палитра нод

- Поиск сверху; группы: Запуск, Источник, Сканеры, Логика, AI, Анализ, Вывод, Уведомления.
- Карточка ноды в палитре: иконка, название, одна строка «что делает».
- Наведение на ноду в палитре показывает её входы и выходы.

### 5.4. Итоги запуска (правый инспектор)

Вкладки: **Находки · AI-отчёт · Score · Данные · Журнал**.
- Находки: фильтр «Новые / Существующие / Все» (если в графе есть Diff Scanner), критичность, категория. Клик по
  находке — карточка: где, почему такая критичность, что сделать, фрагмент (замаскирован), «AI AutoFix» →
  diff → «Скачать .patch» / «Создать PR» → «Применить патч и перепроверить» (вся логика текущей страницы
  «Разбор PR» переезжает сюда).
- AI-отчёт: вывод, порядок исправления, индикатор доверия (проверки валидатора).
- Score: значение, дельта, Priority Fix List, AI-план спринта.
- Данные: что передала каждая нода (то, что сейчас «Данные между нодами»).
- Журнал: ноды по порядку со статусом и длительностью; уведомления и их доставка.
- Действия: «Скачать submission.json / report.md / report.html», «Сравнить с предыдущим», «Открыть полный
  отчёт» (полноэкранная панель с текущей страницей деталей запуска).

### 5.5. Выдвижные панели второго уровня

- **История**: запуски текущей проверки (переключатель «все проверки»), фильтры, выбор двух для сравнения. Клик
  по запуску — он показывается на холсте и в «Итогах».
- **Шаблоны**: галерея с поиском, рейтингом и отзывами. «Использовать» открывает «Новую проверку» с выбранным
  шаблоном на шаге 2. «Опубликовать текущую» — из меню «⋯».
- **CI/CD**: текущая страница «Интеграция», привязанная к открытой проверке.
- **Обзор**: дашборд пространства (Score и тренд, находки по типам и уровням, последние запуски).
- **Настройки**: AI-провайдер, секреты, allowlist, участники, расписания, проекты, интерфейс.

### 5.6. Маршруты

- `/` → последняя открытая проверка или «Новая проверка», если проверок нет.
- `/c/:workflowId` — проверка; `?run=<id>` — показать запуск; `?panel=history|templates|ci|overview|settings`.
- `/runs/:id` **сохраняется** (ссылки из уведомлений, CI и `report.html`): ведёт на
  `/c/<workflow>?run=<id>`; для запуска без сценария открывает полный отчёт.
- Старые адреса (`/workflows/:id`, `/pr`, `/templates`, `/integration`, `/settings`, `/projects`) перенаправляют на
  новые эквиваленты.

### 5.7. Визуальный стиль

- Светлая тема по умолчанию, тёмная — переключателем. Тёмная тема на холсте выглядит эффектнее, поэтому при
  запуске анимации рассчитаны на обе темы.
- Палитра цветов наследуется от текущих токенов (`index.css`); от вёрстки макета Figma отказываемся.

## 6. Backend

### 6.1. Ссылка на любой публичный репозиторий (вариант А)

- `POST /api/repos/attest` `{workspace_id, url, confirm: true}`. Делает следующее:
  - проверяет URL тем же `check_git_url` (только https, без учётных данных и query);
  - отклоняет хосты, которые резолвятся в приватные, локальные или служебные адреса (тот же SSRF-фильтр, что и
    у исходящих запросов);
  - добавляет URL в allowlist пространства (`RepoAllowlist`, `allow_write=false`);
  - пишет аудит `repo.attest` (кто, IP, URL, текст подтверждения).
- Роль: `developer` и выше (участник может проверить свой репозиторий без админа).
- `confirm` обязателен: без галочки — 422.
- Клонирование не меняется: `clone_repo` по-прежнему требует, чтобы URL был в allowlist. Подтверждение просто
  добавляет его туда.
- Репозиторий организаторов остаётся только на чтение (`is_readonly_repo`).

### 6.2. Создание проверки одним запросом

- `POST /api/checks` `{workspace_id, name?, source: {mode: git_url|upload|path|training, url?, ref?, upload_id?},
  start: {template_id} | {blank: true} | {prompt}}` → `{workflow_id}`. Делает следующее:
  - создаёт сценарий из шаблона, пустого графа или AI-генерации;
  - записывает источник в `source.repo`;
  - незаполненные необязательные для создания параметры оставляет пустыми и не возвращает 400.
- Если делать через существующие эндпоинты (`/templates/{id}/use`, `/workflows`) удобнее — допустимо. Требование
  одно: создание не блокируется параметрами уведомлений, а источник подставляется сам.

### 6.3. Автосохранение

- Используем существующий `PUT /api/workflows/{id}` с дебаунсом ~800 мс. Конфликт версий (если есть) показывается
  тостом с предложением перезагрузить.

## 7. Анимации выполнения («неон»)

Требование: плавные красивые анимации **от начала до конца запуска**, а не только между нодами. Работающая нода
переливается неоном по краям.

| Момент | Что видно |
| --- | --- |
| Нажали «Запустить» | Холст слегка затемняется (оверлей 8 %, 200 мс). Все ноды запуска переходят в «ожидание»: приглушённая обводка с медленной «дышащей» пульсацией. Неактивные ветки не трогаем, пока движок их не пропустит |
| Нода начала работу | Обводка зажигается: **конический градиент** (зелёный → бирюзовый → лаймовый → зелёный) вращается по периметру (~1,8 с на оборот, бесконечно), внешнее свечение 12–18 px пульсирует. Карточка чуть поднимается (scale 1.02, тень) |
| Данные пошли по ребру | По ребру бежит светящийся «пакет» (анимация `stroke-dashoffset` + частица); у ребра появляется значок количества (например, «15») с мягким pop-in |
| Нода успешно завершилась | Вращение замедляется и гаснет в ровную зелёную обводку; короткая вспышка (300 мс) и «поп» галочки |
| Ошибка | Красный неон, лёгкое покачивание (2 цикла по 80 мс), красная иконка; ребро после неё не загорается |
| Нода пропущена (ветка IF) | Плавно уходит в 45 % прозрачности, обводка пунктиром |
| Запуск завершён | Финальная «волна»: свечение пробегает по всем успешным нодам в порядке выполнения (по 60 мс на ноду), затем холст возвращается к обычному виду. В инспекторе открываются «Итоги», счётчик находок «досчитывает» до значения |

- Реализация: только CSS (`@property --angle` + `conic-gradient` в псевдоэлементе с маской рамки; `@keyframes`
  для свечения), анимируем `transform`/`opacity`/кастомное свойство — без перерисовки layout. Никаких тяжёлых
  библиотек анимаций.
- `prefers-reduced-motion: reduce` → статичные цветные обводки без вращения и бегущих частиц.
- Производительность: 30+ нод одновременно не должны ронять FPS ниже 50 на обычном ноутбуке (проверка
  Performance-профилем в Chrome/Edge).
- Цвета неона берутся из токенов темы, чтобы в обеих темах было читаемо.

## 8. Подходы (рассмотрены)

1. **Рабочее пространство в духе n8n — выбран пользователем.** Один экран: проверки слева, холст в центре,
   инспектор справа. Второстепенное — выдвижными панелями. Максимум удобства, ТЗ ссылается на n8n. Самая большая
   переделка навигации.
2. Эволюция текущих страниц: полноэкранный конструктор + стартовый экран, меньше меню. Дешевле, но
   перегруженность и переходы между страницами остаются.
3. Мастер на первом месте, конструктор как «расширенный режим». Быстро для жюри, но конструктор становится
   второстепенным — против цели и критерия ТЗ. Отброшен.

## 9. Решения, принятые пользователем

- Главный пользователь — жюри, тестирует на своём новом репозитории.
- Репозиторий по ссылке: **вариант А** (любой публичный + подтверждение + аудит).
- Каркас: **вариант 1** (рабочее пространство).
- Неоновые переливающиеся анимации нод на протяжении всего запуска.
- Макеты Figma не обязательны.

## 10. Решения, принятые мной (можно поправить)

- Автосохранение вместо кнопки «Сохранить».
- «Проект» уходит из главного пути и остаётся в настройках.
- Страница «Разбор PR» не отдельная: её логика живёт в «Итогах → Находки → AutoFix».
- Дашборд становится панелью «Обзор».
- Палитра — плавающая панель поиска (кнопка «+», `Tab`), с перетаскиванием.
- Роль для подтверждения репозитория — `developer`.

## 13. Внешние LLM API через прокси (по `LLM_PROXY.md`)

Добавлено по запросу пользователя при согласовании. `LLM_PROXY.md` описывает схему из другого проекта
(`backend/ai/llm_client.py`); здесь она переложена на нашу архитектуру провайдеров (`backend/app/ai/providers`).

**Зачем:** подключать внешние API (прежде всего Google Gemini) из сети, где они недоступны напрямую. Для этого
нужны пул ключей, пул прокси и устойчивые повторные попытки.

- **Новый провайдер `gemini`** (`@register_provider`): нативный `POST {base}/models/{model}:generateContent`,
  ключ только в заголовке `x-goog-api-key`, `responseMimeType: application/json` для JSON-ответов. Ответ — склейка
  `parts[].text` первого кандидата.
- **Пул для любого провайдера** (в т.ч. `openai_compat`) в `ProviderConfig` и общем `_request`:
  - несколько ключей (каждый — секрет в зашифрованном хранилище);
  - модели-фолбэки;
  - список прокси (новый вид секрета `proxy`; форматы `host:port:login:password`, `host:login:password` +
    порт по умолчанию, полный URL);
  - протокол `auto | http | https | socks5 | socks5h`;
  - число попыток (авто: `min(max(ключей, кандидатов прокси, 3), 6)`, где `auto`-прокси считается за 2).
- **Попытка за попыткой:** модель `models[min(i, n-1)]`; ключ и прокси — случайные из ещё не использованных в
  этом вызове, затем из всех. Пауза 2, 4, 6, 8, 10 с. Таймаут соединения `min(timeout, 10)`, жёсткий дедлайн
  `timeout + 5`.
- **Неудачная попытка:** любой статус ≠ 200, пустой текст, битый JSON, сетевая ошибка, таймаут, ответ не прошёл
  проверку вызывающей стороны. Когда попытки кончились — `LLMError` с последней причиной, и срабатывает уже
  существующий детерминированный fallback.
- **Автоопределение протокола прокси:**
  - сниффинг без отправки логина и пароля: SOCKS5-приветствие `05 01 00`, затем `CONNECT`, по 3 с;
  - кэш удачного протокола на 10 минут в памяти; перебор `http → socks5 → https`;
  - успех запоминается, провал сбрасывает кэш.
- **SSRF:** через прокси IP не закрепляется (имя резолвит прокси). Поэтому проверяется и адрес API, и адрес
  прокси: оба должны быть публичными или явно разрешены. Прямые запросы — как сейчас, с закреплением IP.
- **Маскирование:** ключи и логины/пароли прокси регистрируются в `Masker`. В логах только `scheme://host:port`
  и последние 4 символа ключа. Ключ никогда не попадает в URL.
- **Настройка:**
  - через UI («Настройки → AI»): провайдер, модель, фолбэки, ключи (несколько), прокси, протокол, попытки;
  - через окружение (`backend/.env`, имена как в `LLM_PROXY.md`: `LLM_ENABLED`, `LLM_PROVIDER`,
    `GEMINI_API_KEY`, `GEMINI_KEYS_COUNT`, `GEMINI_MODEL`, `GEMINI_FALLBACK_MODELS`, `GEMINI_MAX_RETRIES`,
    `GEMINI_PROXIES`, `GEMINI_PROXY_SCHEME`, `GEMINI_PROXY_PORT`, `GEMINI_BASE_URL`, `OLLAMA_URL`,
    `OLLAMA_MODEL`) — это платформенный провайдер по умолчанию для пространств без своих настроек;
  - секреты из окружения в БД не пишутся.
- **Диагностика:** кнопка «Проверить соединение» шлёт по одному маленькому запросу через каждый прокси (для
  `auto` — по каждому протоколу) и напрямую. Ответ: `OK`/`FAIL`, время, причина без секретов. CLI-аналог —
  `python -m app.ai.check_llm`.
- **Зависимость:** `httpx[socks]` (`socksio`) — для SOCKS-прокси.
- **Тесты** (контрактные, на локальных HTTP- и SOCKS-серверах, без реальной сети):
  - ротация ключей, прокси и моделей; паузы подменяются в тестах;
  - определение протокола и кэш;
  - отсутствие секретов в ошибках и логах;
  - SSRF для прокси;
  - разбор переменных окружения.
