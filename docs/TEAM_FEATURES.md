# Фичи команды сверх ТЗ (§12А)

## 1. Diff-aware scan: сканирование изменений и блокировка PR

**Зачем.** Небольшая команда не может сразу починить сотни старых находок. Если сканер блокирует всё подряд, его просто отключают. Поэтому принцип такой: «за старый код не отвечаем, но новое не пропустим». PR блокируют только находки, которые появились в этом diff.

### Откуда берётся diff

| Режим | Источник контекста | Модуль |
|---|---|---|
| CI (CLI) | CLI выполняет в рабочей копии `git diff --unified=0 --find-renames -w --ignore-blank-lines <base>...HEAD`, `git show <merge-base>:<file>` для всех файлов сборки, `git blame --porcelain -L` по изменённым диапазонам и загружает результат как `diff_context` вместе с архивом | `cli/aisw_ci.py` → `analyzers/diff/git.py::load_uploaded` |
| Вебхук / `git_url` / `path` с `.git` | git на стороне платформы, только чтение. Base берётся из события (`pull_request.base.sha`, `before` у push; при `000…0` — ветка из ноды); shallow-клон углубляется `--deepen`, не более 5 раундов | `analyzers/diff/git.py::compute_platform` |
| Нет git и нет diff | `on_missing_diff = fail` (по умолчанию) — понятная ошибка ноды; `treat_all_as_new` — все находки считаются новыми | нода `scanner.diff` |

**Безопасность git**:
- команды идут через `repo_guard`: `core.hooksPath=/dev/null`, `core.fsmonitor=false`, `diff.external=`, флаги `--no-ext-diff --no-textconv`;
- аргументы передаются списком с разделителем `--`, ref и sha проверяются регулярными выражениями;
- fetch разрешён только по https, токен передаётся в заголовке, а не в URL;
- поиск `.git` не поднимается выше корня сканирования: для `path` это корень из `APP_SCAN_ROOTS`, для `upload` и `git_url` — рабочая копия.

### Карта изменений (`analyzers/diff/hunks.py`)

Используется только **три точки** (`base...head`): diff считается от merge-base. С двумя точками в diff попали бы коммиты, которые влили в base уже после ответвления. Тест `test_three_dots_exclude_commits_landed_on_base_after_branching` это проверяет.

Результат разбора: `{path: {new_lines, hunks[{old_start, old_count, new_start, new_count, header}], renamed_from, status}}`.

Особые случаи:
- чистое переименование не даёт новых строк;
- удалённые и бинарные файлы не содержат новых строк;
- переформатирование не считается изменением (`-w --ignore-blank-lines`);
- пути в кавычках (не-ASCII) декодируются;
- пути diff, заданные от корня репозитория, приводятся к путям находок от корня проекта (например, отрезается `training-project/`).

Glob-шаблоны по умолчанию: `*.kt *.kts *.gradle *.properties *.yml *.yaml *.toml gradle.lockfile`.

### Классификация (`classifier.py`, `sca_diff.py`)

Анализаторы работают по **полным** файлам, иначе теряется контекст: константа может быть на 10-й строке, а использование на 50-й. Классифицируется уже готовый набор находок.

- **SECRET/SAST**: находка `new`, если хотя бы одна строка диапазона `[line, end_line]` попала в `new_lines`. Для межфайловых находок (IDOR) достаточно, чтобы diff задел основное место **или** любое из `alternate_locations`.
- **SCA — по версиям, а не по строкам.** Тот же SCA-анализатор запускается на базовых версиях файлов сборки, развёрнутых во временной директории. Ключ сравнения — `(group, artifact, advisoryId)`:
  - `new` — уязвимости не было в base. Сюда попадает и повышение версии только через `gradle.properties`, `val`, version catalog или lockfile;
  - `existing` — уязвимость была в base; если версия при этом изменилась, ставится `version_changed: true`;
  - уязвимости, которые были в base и исчезли, попадают в список `fixed_in_diff`.
- **Атрибуция** новых находок: `introduced_in_commit` и `author` берутся из `git blame --porcelain`. `author` — персональные данные: он виден только участникам workspace, не попадает в промпты LLM, в шаблоны и в комментарий к PR.

### Вердикт и возврат в пайплайн

- `FAIL` — есть хотя бы одна новая находка с severity не ниже порога. Порог по умолчанию `CRITICAL`, тот же, что у `ci_gate`. Иначе `PASS`.
- `report_only` — вердикт всегда `PASS`, но в `would_fail_reason` записывается, почему было бы `FAIL`.
- Нода `scanner.diff`:
  - входы: `repo` и `findings`;
  - выходы: `new_findings`, `existing_findings`, `verdict` (`verdict`, `threshold`, `new_counts_by_severity`, `existing_count`, `fixed_in_diff`, `base_sha`, `head_sha`, `merge_base`).
- `output.ci_gate` со входом `verdict` учитывает только новые находки.
- `GET /api/v1/ci/runs/{id}/verdict` возвращает **200** при PASS и **422** при FAIL, а также новые находки с маскированными сниппетами. Поле `verdict` есть и в `GET /api/v1/ci/runs/{id}`.
- CLI возвращает exit 0 при PASS, 1 при FAIL, 2 при ошибке платформы.
- Commit status при FAIL: `failure` с текстом «N new critical — merge blocked».
- Комментарий в PR/MR, всегда один на PR (маркер `<!-- aisw-report -->`, при каждом push обновляется, а не создаётся заново):
  - в вебхук-режиме его пишет платформа (`app/ci/status.py::upsert_comment`);
  - в CLI-режиме тот же Markdown пишется в `$GITHUB_STEP_SUMMARY` и публикуется при наличии `GITHUB_TOKEN`/`GITLAB_TOKEN`.
- UI: бейдж `diff: PASS/FAIL` в шапке запуска; переключатель «Новые / Существующие / Все»; в карточке находки — hunk, коммит и автор.

### Демо

```bash
# API должен видеть каталог демо и mock GitHub:
APP_SCAN_ROOTS=$PWD/fixtures,/tmp/aisw-demo APP_SSRF_ALLOW_HOSTS=127.0.0.1:18090 ...uvicorn...
AISW_URL=http://localhost:8000 AISW_DEMO_ROOT=/tmp/aisw-demo scripts/demo_diff.sh
```

Что делает скрипт:
1. Создаёт во временной директории git-репозиторий из копии `training-project`. Сами фикстуры не меняются.
2. В ветке добавляет сгенерированный AWS-ключ (случайный, не `EXAMPLE`; в наш репозиторий не попадает).
3. Отправляет PR-вебхук на mock GitHub. Результат: **FAIL**, статус «2 new critical — merge blocked», комментарий с таблицей новых находок.
4. Откатывает коммит с ключом. Результат: **PASS**, тот же комментарий обновлён, 15 старых находок помечены `existing`.

## 2. Security Score: тренд безопасности проекта и Priority Fix List

> Security Score — **метрика внутреннего тренда проекта**, а не рейтинг между проектами. Она отвечает на вопрос
> «стало лучше или хуже после этого коммита/спринта», а не «какой проект безопаснее».

### Формула (`backend/app/scoring/formula.py`, `formula_version = "1"`)

```
penalty = Σ weight(severity) × novelty(finding)        — только находки с confidence ≥ 0.6
weight:  CRITICAL 10 · HIGH 5 · MEDIUM 2 · LOW 1
novelty: new 1.5 · existing 1.0 (без diff-контекста — 1.0)
S       = S0 × max(1, sqrt(LOC / 1000)),  S0 = 50
score   = round(100 · exp(−penalty / S))               ∈ [0, 100]
```

- **Экспонента** вместо линейного вычитания: score никогда не уходит в минус, первая критичная находка заметно
  роняет score, а сотая — уже почти нет (насыщение), поэтому «грязный» проект всё равно видит прогресс от исправлений.
- **Нормализация по LOC** (корень, а не линейная) — большой проект не получает «бесплатный» высокий score, но и не
  наказывается за размер. До 1000 LOC масштаб не меняется.
- **Порог уверенности** совпадает с официальной выгрузкой (`OFFICIAL_MIN_CONFIDENCE = 0.6`): то, что не попало бы в
  `submission.json`, не влияет на score.
- Расчёт детерминирован и не зависит от порядка находок (тест с перемешиванием).
- Параметры (`s0`, `weights`, `novelty`, `min_confidence`) переопределяются для workspace: `GET/PUT /api/settings/score`
  (только admin, аудит).

### Калибровка S0

| Набор | penalty | S0 = 25 | **S0 = 50** | S0 = 100 |
|---|---|---|---|---|
| учебный репозиторий (1C + 7H + 7M), 316 LOC | 59 | 9 | **31** | 55 |
| мутант clinic-appointments | 36 | 24 | **49** | 70 |
| мутант library-loans | 35 | 25 | **50** | 70 |
| мутант parcel-lockers | 35 | 25 | **50** | 70 |

Все наборы меньше 1000 LOC, поэтому S = S0 и score зависит только от penalty. Числа получены прогоном собственных
анализаторов по `fixtures/` с текущими весами.

При S0 = 25 учебный проект с 15 настоящими проблемами оказывается около нуля (9), и исправление одной HIGH почти не
видно. При S0 = 100 тот же проект выглядит «нормально» (55). S0 = 50 даёт «явно плохо, но не безнадёжно» (~30 для учебного, ~50 для мутантов с меньшим числом находок) и сохраняет различимость наборов, и
каждая исправленная HIGH даёт видимые +3…+5. Демо: поднятие `commons-text` и `jsoup` до исправленных версий даёт
**31 → 41 (+10)**.

### Дельта и тренд (`scoring/service.py`, `scoring/trend.py`)

- Score считается post-run хуком (`record_score`) для **каждого** успешного запуска с анализаторами и сохраняется в
  `runs.score / score_delta / score_details / loc / score_formula_version / scanner_set_signature`.
- `delta` считается к предыдущему успешному запуску того же проекта **с той же `scanner_set_signature`** (отсортированный
  набор нод-сканеров). Если поменять набор сканеров или версию формулы, дельта не сравнивает несравнимое: она
  становится `null`, а на графике появляется маркер «сменился набор сканеров / формула».
- Тренд считается МНК-наклоном (очков в неделю) по последнему сравнимому сегменту за 7/30/90 дней. При < 3 точках
  выводится «недостаточно данных».
- `GET /api/projects/{id}/score/history?period=7d|30d|90d` возвращает точки (score, delta, commit, verdict), маркеры и тренд.

### Priority Fix List (`scoring/priority.py`)

`priority = weight × novelty / fix_effort`, где `fix_effort` 1..5 берётся из таблицы по классу находки (зависимость:
1, «заменить строку»; IDOR: 3, «правка авторизации»; …) либо из AI-плана, если LLM прислала целое 1..5 для известного
id (источник `ai` / `default` виден в UI). Для каждой позиции детерминированно считаются:

- `expected_gain`: на сколько вырастет score, если исправить только её;
- `cumulative_gain`: прирост от исправления всех позиций до неё включительно.

Это честные числа из той же формулы: LLM их не придумывает.

### AI-план на спринт (`scoring/sprint_plan.py`, `POST /api/runs/{id}/sprint-plan`)

- В LLM уходит только `{score, delta, trend_per_week, top_findings:[{finding_id, class, severity, novelty,
  fix_effort, expected_gain}]}`. Пути, сниппеты и авторы не передаются (это проверяет тест), всё проходит через маскирование.
- Ответ — JSON `{summary, plan:[{finding_id, action, reason}], defer:[…], projected_score, efforts?}`.
- Валидатор:
  - неизвестные и повторные `finding_id` отбрасываются;
  - `projected_score` **пересчитывается** формулой по id из `plan`; если LLM ошиблась больше чем на 1, её число
    заменяется и ставится флаг `corrected_numbers`;
  - CVE/GHSA, которых нет в базе и находках, вырезаются;
  - `fix_effort` вне 1..5 отклоняется;
  - при невалидной структуре делается одна повторная попытка.
- Без LLM (или если LLM недоступна) план строится детерминированно: позиции из Priority Fix List набираются в бюджет
  спринта (8 очков трудозатрат), результат помечен `ai_generated: false`. План сохраняется как `ai_reports.kind = "sprint_plan"`.

### В графе и UI

- Нода `analysis.security_score` выводит `{value, delta, penalty, scale, loc, breakdown, priority}` и кладёт score в
  контекст: `logic.if_else` может ветвиться по `score.value < 50 and score.delta < 0`.
- Dashboard (`GET /api/dashboard`): score с цветной дельтой, тренд, график с коммитами и маркерами смены набора,
  топ-3 исправлений с «ожидаемо +N», карточка AI-плана.
- Вкладка **Score** в деталях запуска: разбивка штрафа, полный Priority Fix List, AI-план и оговорка про внутренний тренд.

## 3. AI AutoFix: патч, самопроверка сканером и Pull Request

AutoFix превращает находку в проверенный патч. LLM только **предлагает** изменение. Принимается оно лишь после того,
как наши же анализаторы на пропатченной копии проекта подтвердили: находка исчезла, новых не появилось.

### Применимость и покрытие (`app/autofix/coverage.py`)

У каждого правила в метаданных есть `autofix: llm | deterministic | none`:
- `deterministic`: SCA, обновление версии зависимости (без LLM);
- `llm`: секреты (вынос в переменную окружения без значения по умолчанию), SQL (параметризация), TLS, CORS,
  route/object-authorization и др.;
- `none`: архитектурные решения (небезопасная десериализация, отключённый CSRF, приватный ключ в репозитории):
  только рекомендация.

Покрытие считается из этих метаданных (`GET /api/autofix/coverage`) и показывается в UI:
**«AutoFix доступен для 27 из 30 правил»** (26 llm, 1 deterministic, 3 none).

### Детерминированный SCA-bump (`sca_bump.py`)

Версия поднимается до ближайшей `fixedVersion` ветки **в месте определения**: строковый литерал, `val`,
`gradle.properties`, version catalog, `extra`. Места берутся из того же разбора, которым пользуется SCA-анализатор,
поэтому правится ровно то, из чего анализатор вывел версию. Если зависимость есть в `gradle.lockfile`, строка в нём
тоже обновляется, и в PR добавляется пометка «перегенерируйте локи: `./gradlew dependencies --write-locks`».
Тесты покрывают все пять форм, с lockfile и без.

### Контекст для LLM (`context.py`)

- Правило, класс, описание, severity.
- Сниппет ±10 строк с номерами.
- Объемлющая функция или класс (tree-sitter, с лимитом размера).
- Для межфайловых находок — связанные функции из `alternate_locations`.

Секреты маскируются **построчно**: сырые значения берутся из `scan_secrets(collect=…)` и живут только в памяти.
Номера строк маскированного представления совпадают с реальным файлом, поэтому `old_snippet` проверяется по маскам,
а применяется по позициям строк.

Ответ — строго JSON `{file, start_line, end_line, old_snippet, new_snippet, explanation, requires_config}`.

### Валидатор (`validator.py`) — чеклист в UI

1. JSON-схема.
2. Файл входит в контекст находки, строки в пределах файла, имена `requires_config` похожи на имена переменных
   окружения.
3. `old_snippet` дословно (с нормализацией пробелов) совпадает с маскированными строками. Допускается сдвиг до ±3
   строк, он отмечается в чеклисте. Это защита от галлюцинаций.
4. В `new_snippet` нет артефактов маски, исходных значений секретов и новых литералов, похожих на секрет.
5. Патч применяется к **временной копии** проекта; исходники не трогаются.
6. Синтаксис: tree-sitter не даёт новых `ERROR`/missing-узлов (YAML — `safe_load`). Компиляция и Gradle не
   запускаются: проверяемый код никогда не исполняется.
7. Самопроверка: все три анализатора на всей пропатченной копии. Исходная находка должна исчезнуть, новых — 0.

Если проверка не пройдена, LLM получает одну повторную попытку с ошибками валидатора, после чего фикс получает
статус `rejected(reason)`. PR может стать только `validated`.

### PR/MR (`pr/scm.py`, `pull_request.py`)

Запросы идут только через REST; `git push` с токеном в URL не используется.
- **GitHub:** sha base-ветки → `POST git/refs` (`autofix/<finding_id>`) → `PUT contents` (с sha blob) →
  `POST pulls` → метка `security-autofix`.
- **GitLab:** `POST repository/branches` → `POST repository/commits` (`update`) → `POST merge_requests`.

Свойства:
- Идемпотентно: уже существующие ветка и PR/MR обновляются, дубли не создаются.
- Auto-merge нет, в base-ветку ничего не коммитится.
- Разрешено только для репозитория из allowlist с `allow_write=true` и токеном `repo_write_token`. Репозиторий
  организаторов и `fixtures/` запрещены кодом (403). Для них, а также для архивов и каталогов, доступны diff в UI и
  «Скачать .patch».
- Описание PR (шаблон) содержит маскированную находку, объяснение, чеклист проверки, `requires_config` и ссылку на
  запуск. Создание PR пишется в аудит.
- Реальное содержимое файлов в БД не хранится. Для PR исходники восстанавливаются заново, и к ним повторно
  применяется сохранённое предложение (`new_snippet` проверен и не содержит секретов).

### Исходники и хранение

- AutoFix из UI заново получает код: каталог из `APP_SCAN_ROOTS` (копируется), зашифрованный архив (до TTL
  `APP_UPLOAD_RETENTION_HOURS`, по умолчанию 72 ч; затем воркер удаляет файл) или git на точном коммите запуска.
- Результаты хранятся в таблице `autofixes`: вид, провайдер/модель, маскированный patch, шаги валидации, статус,
  `pr_url`, автор.
- Удаляемые строки с секретом в `.patch` маскированы: такой патч предназначен для ревью. Патчи без секретов
  (SCA, SQL) применяются через `git apply`.

### Нода `ai.autofix` и UI

- Нода: вход `findings`; параметры `auto_create_pr` (false), `max_findings` (3), `min_severity` (HIGH),
  `target_branch`, `pr_template`. Выход: `[{finding_id, status, reason, patch, pr_url}]`. Работает на рабочей копии
  запуска, не изменяя её.
- UI: кнопка AutoFix в карточке находки, чеклист, diff «было/стало», `requires_config`, «Создать/Обновить PR»
  (только если запись разрешена), «Скачать .patch», покрытие правил.

### Демо (`scripts/demo_autofix.sh`)

1. PR-вебхук: 15 существующих находок.
2. AutoFix «Встроенный пароль»: 7/7 шагов, пароль вынесен в `LEGACY_IMPORT_PASSWORD`.
3. PR на mock GitHub: 7 REST-запросов.
4. Diff-aware прогон ветки `autofix/…`: **PASS, 0 новых, 14 существующих**.
5. Репозиторий организаторов: SCA-bump `commons-text 1.9 → 1.10.0` + lockfile, только «Скачать .patch».

Настоящей LLM в окружении нет. В демо стоит локальный OpenAI-совместимый endpoint, который строит ответ из
полученного маскированного контекста; в выводе он явно помечен. Валидатор, самопроверка, PR и повторная проверка —
настоящий код продукта.
