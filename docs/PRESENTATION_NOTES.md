# Материалы к презентации

## 1. Проблема и пользователь

**Пользователь** — команда разработки банка: разработчики, тимлид, AppSec-инженер. Сервисы на Kotlin, Spring и
Gradle. Проверки безопасности сегодня либо ручные, либо собраны из разрозненных скриптов, а SaaS-сканеры
неприменимы: код не должен уходить за периметр, правила и выводы нужно объяснять аудитору.

**Цель кейса** — визуальный конструктор проверок без программирования: собрать сценарий из блоков, запустить его
вручную, по расписанию или из CI, получить находки с понятным объяснением и исправлением, уведомить команду и не
пропустить уязвимость в основную ветку.

## 2. Как решение закрывает цель

- **Визуальный редактор.** Drag & drop, типизированные порты, проверка графа до запуска, живая подсветка нод и
  потоков данных, история и сравнение запусков.
- **Собственный движок.** Очередь в PostgreSQL, параллельные ветки, IF/ELSE, таймауты, отмена, расписания без
  дублей, отдельный воркер. Готовых workflow-платформ нет.
- **Собственные анализаторы** SECRET / SCA / SAST: на учебном наборе 15/15 при 0 ложных срабатываниях, на трёх
  мутантах тоже без пропусков.
- **LLM только объясняет.** Каждый её ответ проходит валидатор, без LLM всё работает в детерминированном режиме.
- **Закрытый контур.** Локальная LLM (Ollama), шифрование секретов, маскирование везде, allowlist источников,
  SSRF-защита, аудит.
- **CI/CD.** CLI и вебхуки, статусы и комментарии в PR/MR, «красный» job на Critical.

## 4. Алгоритмы анализаторов

Подробно — [ANALYZERS.md](ANALYZERS.md).

- **SECRET.** Четыре слоя:
  1. сигнатуры: AWS, GitHub, Telegram, Slack, Stripe, Google, JWT с декодированием заголовка, PEM, учётные данные в
     URL и JDBC;
  2. Kotlin AST: семантика имён, «стоки» (заголовки, `setBearerAuth`, `.password()`), fallback-значения
     `getenv() ?: "…"`, `@Value("${k:default}")`, а также восстановление токена, собранного из нескольких литералов,
     Base64 или `reversed()` через собственный константный резолвер;
  3. конфигурации YAML, properties, env, JSON, XML;
  4. энтропия — только как слабый сигнал.

  Ложные срабатывания отсекаются: плейсхолдеры, `${ENV}` без значения по умолчанию, имена переменных и заголовков.
- **SCA.** Разбор Gradle Kotlin DSL по AST: литералы, `val`, `extra`, `gradle.properties`, version catalog,
  `platform()`. `gradle.lockfile` важнее объявленной версии. Собственное сравнение версий с диапазонами
  `introduced/fixed/lastAffected`, собственный калькулятор CVSS v3. Remediation — ближайшая исправленная версия.
- **SAST.** tree-sitter-kotlin → собственное промежуточное представление → межпроцедурный taint (запрос →
  SQL / файл / процесс), граф вызовов. Модель Spring Security: порядок `requestMatchers`, перекрытие `permitAll`,
  CSRF, CORS с credentials. IDOR: `@PathVariable` без проверки владельца. Слабая криптография, отключённая проверка
  TLS, небезопасная десериализация, открытый actuator.

## 5. Классификация находок

- **Единая модель `Finding`:** категория, класс, правило, путь и строки (+ `alternateLocations`), severity,
  confidence, CWE, advisory, remediation, маскированный сниппет, стабильный `id`.
- **Severity.** SCA — CVSS v3. SECRET — по классу, ±1 за продакшн-код или тесты. SAST — матрица «класс ×
  достижимость без аутентификации».
- **Confidence:** 0.9–0.95 — сигнатура или точный шаблон, 0.8–0.88 — межпроцедурный вывод, 0.45 — энтропия.
  Официальная выгрузка берёт находки с confidence ≥ 0.6.
- **Diff-aware:** `new` / `existing` относительно base-ветки.

## 6. Передача данных между нодами

- Конверт `Envelope(type, data, meta)`. Типы портов: `trigger`, `repo`, `findings`, `report`, `json`, `text`,
  `bool`, `any`. Несовместимое соединение редактор не даёт сохранить.
- Рабочая копия кода передаётся ссылкой (`repo.root`) и в API не попадает.
- Каждое ребро пишет событие `edge.data` с размером и кратким содержимым (маскированным). UI показывает «поток данных».
- Выражения и шаблоны работают только с подготовленным контекстом (`findings.count`, `severity.max`, `score`,
  `verdict`), `eval` нет.

## 7. LLM: какая и как передаются данные

- **Провайдер** настраивается в UI: Ollama (локально, бесплатно — `qwen2.5:7b`, `llama3.1:8b`) или любой
  OpenAI-совместимый API (OpenRouter `:free`, Gemini, LM Studio, vLLM).
- **Что уходит в LLM:** только маскированные находки и ±3 строки контекста. Значения секретов заменены на
  `ab…(len=N)`, весь репозиторий не отправляется. Ключи провайдеров и токены регистрируются в маскировщике при
  расшифровке.
- **Честно:** в окружении разработки реальной LLM не было. Слой проверен контрактными тестами на локальных
  HTTP-серверах в форматах OpenAI и Ollama. Детали — [AI.md](AI.md).

## 8. Проверка ответа LLM — реальные примеры из тестов

| Что делает модель | Что делает валидатор | Тест |
| --- | --- | --- |
| Пишет «также CVE-2099-99999 и GHSA-aaaa-bbbb-cccc» | Вырезает 4 выдуманных id, оставляет настоящий advisory находки, ставит флаг `hallucinated_ids` | `tests/ai/test_validator.py::test_hallucinated_cve_removed_and_flagged` |
| Предлагает `safe_version: "0.0.1-invented"` | Заменяет на ближайшую из `fixedVersions`, метрика `safe_version_corrected` | `test_safe_version_checked_against_fixed_versions` |
| `fix.before` не совпадает с файлом, чужой путь или строки | Исправление отбрасывается, объяснение остаётся | `test_fix_with_wrong_path_before_or_lines_is_dropped` |
| Ссылается на `Unknown.kt:12` | Ссылка вырезается | `test_inline_file_reference_to_unknown_file_is_removed` |
| Чужие или повторные `finding_id` | Удаляются и учитываются в метриках | `test_unknown_and_duplicate_ids_dropped` |
| Невалидный JSON | Одна попытка исправления, затем детерминированный отчёт (не молча) | `tests/ai/test_report_service.py` |
| AutoFix с ошибкой синтаксиса или новой находкой | Отклоняется на шаге `syntax` / `self_check` | `tests/api/test_autofix_api.py` |

**Оценка полезности.** Индикатор доверия в UI показывает долю принятых пунктов (`valid_items/total_items`),
исправленные и отброшенные решения. Метрики берутся из журнала валидатора каждого отчёта. Цифр по реальной модели нет
(см. п. 7). На демо с подключённой LLM смотрите панель «Доверие» в AI-отчёте.

## 9. Архитектура и расширение

Схема — [ARCHITECTURE.md](ARCHITECTURE.md).

- **Добавить ноду за минуту.** Один файл в `backend/app/nodes/<группа>/` с `@register_node` (пример на ~20 строк в
  README). Она сама появится в API, в палитре редактора с формой из JSON Schema и в документации. Движок, API и
  фронтенд не меняются, это проверяется тестом.
- **Внешний сервис** (Slack, Jira) — нода-уведомление. HTTP идёт через `safe_request` (SSRF-фильтр), секрет — через
  `ctx.secret()`.
- **Локальная LLM.** `docker compose --profile ollama up -d` → в настройках `ollama`, `http://ollama:11434`. Код не
  меняется.

## 10. Реализованные задачи со звёздочкой

1. **Публичная библиотека шаблонов.** Публикация с очисткой секретов, URL и chat_id и заменой их параметрами;
   поиск, фильтры, сортировка; превью графа; рейтинг, отзывы, избранное; версии; «использовать» создаёт копию.
2. **CI/CD.** Генератор YAML для GitHub Actions и GitLab CI, CLI без зависимостей (exit 1 на Critical), вебхуки с
   подписью и идемпотентностью, статусы и комментарии в PR/MR. См. [CI_CD.md](CI_CD.md).
3. **AI-генерация сценария из текста** и правка графа в чате с предпросмотром и «применить / отклонить». Граф
   проходит тот же валидатор, что и ручной.

## 11. Фичи команды — обоснование для жюри

Подробно — [TEAM_FEATURES.md](TEAM_FEATURES.md).

- **Diff-aware проверки:** «вы не виноваты в старом коде, но мы не пропустим новое». Существующие проблемы видны, но
  не блокируют merge; новая уязвимость в PR даёт FAIL. Это снимает главный барьер внедрения сканеров в legacy-код.
  Учитываются переименования, сдвиги строк, изменения пробелов и межфайловые находки.
- **Security Score — метрика внутреннего тренда, а не рейтинг между проектами.** Формула прозрачна и откалибрована на
  учебном наборе; дельта считается только между запусками с тем же набором сканеров. Priority Fix List показывает,
  что даст наибольший прирост. AI-план спринта проходит проверку чисел.
- **AI AutoFix «проверен нашим же анализатором».** Патч применяется к копии, проверяется синтаксис (tree-sitter), и
  все три анализатора подтверждают: находка устранена, новых нет. Только после этого доступен PR, без auto-merge.
  SCA обновляется детерминированно, без LLM. Для репозитория организаторов — только `.patch`.

## 12. Планы развития

- Языки: Java и TypeScript для SAST, Maven и npm для SCA.
- Импорт OSV / GitHub Advisory в локальный справочник по расписанию, без выхода кода наружу.
- SARIF-экспорт и загрузка в GitHub Code Scanning.
- Подавления находок с обоснованием и сроком, ревью подавлений.
- SSO (OIDC/LDAP), распределённый rate limit, Kubernetes Helm-чарт.
- Оценка качества объяснений на реальной локальной модели (набор эталонных ответов, A/B промптов).

## 13. Сценарий живой демонстрации (≈10 минут)

Подготовка: `cp .env.example .env && docker compose --profile mock up -d --build` → http://localhost:8080.

1. **Регистрация** → личный workspace. Настройки → AI: Ollama (профиль `ollama`) или пропустить и показать
   детерминированный режим.
2. **Проект** «training-project»: источник `path` →
   `/app/fixtures/organizer-training/training-project` (или git `https://github.com/TBagirov/training` — он в
   allowlist по умолчанию).
3. **Редактор:** перетащить `trigger.manual → source.repo → [secrets, sca, sast] → merge →
   if_else(severity.max >= HIGH) → ai.report → report_export + notify.webhook`; ветка `false` → `notify.webhook`.
   Webhook — `http://mock:8025/demo`. Для Telegram: `APP_TELEGRAM_API_BASE=http://mock:8025` в `.env`, любой токен.
4. **Запуск:** живая подсветка, 15 находок (1 Critical, 7 High, 7 Medium), ветка `false` пропущена. AI-отчёт с
   индикатором доверия. На http://localhost:8025/_received видно доставленное уведомление.
   `submission.json` скачивается.
5. **Security Score** на вкладке запуска и на дашборде: разбивка штрафа, Priority Fix List, AI-план.
6. **AutoFix** у находки SCA → чеклист и diff → «Скачать .patch» (репозиторий организаторов только для чтения).
7. **Шаблоны:** «Опубликовать как шаблон» → поиск в библиотеке → «Использовать».
8. **Интеграция:** сгенерировать YAML для GitHub Actions, выпустить API-токен.
9. **AI-генерация** (с LLM): «Каждый день в 14:00 проверять секреты и SCA, при Critical — письмо» → граф → чат
   «добавь Telegram».
10. **Diff-aware и PR AutoFix:** `make demo-diff` и `make demo-autofix` на dev-стеке (см. [CI_CD.md](CI_CD.md)).
    Результаты: FAIL → комментарий в PR → PASS; PR `autofix/…` на mock GitHub, повторный прогон — 0 новых.

Короткая автоматическая проверка того же сценария: `make smoke` (15 находок, `submission.json`, вебхук доставлен,
score посчитан).
